## 已完成的业务基础

第一阶段已导入两家企业、两名用户、40张发票、48条银行流水和五条初始规则记录。金额以整数分存储；发票总额、银行收入、银行支出分别计算。甲企业九月采用用途规则2.0版，每张必须填；乙企业采用1.0版，金额大于等于1000元才必填。已停用旧规则不参与检查。

U001可查看两家企业并修改发票用途、备注；U002仅能查看甲企业。发票用企业和发票编号共同定位，银行资料只读。每次保存与审计在同一事务提交，并通过新连接回读。原始材料、当前业务数据和临时测试数据分开保管。

## 本阶段增加的能力

| 能力 | 实现方式 | 使用边界 |
| --- | --- | --- |
| 本地模型接入 | 标准库HTTP请求Ollama的 `/api/chat`，使用工具调用协议 | 需本机Ollama服务和已下载模型 |
| 模型决策循环 | 模型选择totals、check、invoice、prepare_update工具，再根据结果回答 | 每轮最多5次模型请求，单次最多8个工具请求 |
| 信息不足时追问 | 提示模型先明确月份、发票和用户提供的用途 | 月份默认不填，不替换成当前月 |
| 同会话补充和更正 | 保留最近完整对话轮及查询确定的业务月份 | 新启动不恢复任务，不能视为跨会话记忆 |
| 修改草稿 | 模型提议用途或备注，程序校验后展示草稿 | 尚未保存，不允许模型直接写数据库 |
| 明确保存和回读 | 用户输入 `/confirm` 后程序保存并回读 | `/cancel`取消；新问题使旧草稿失效 |
| 上下文长度控制 | 只保留最近最多4轮完整消息，按字符预算移除旧轮 | 这是基础长度控制，不是精确token计量或长期摘要 |
| 运行记录 | 按会话写入JSONL，记录实际模型输入、输出、工具参数和结果 | 日志用于追溯，不会自动作为跨会话记忆载入 |

模型不接收可改写身份或企业的工具参数，入口固定当前身份和企业。自然语言声称自己是管理员不会改变工具权限。切换企业需退出并重新选择入口。当前仍是比赛演示身份选择，没有账号登录认证。

程序进一步检查修改值的来源：用途和备注须为用户本轮明确提供的非空文本，不能来自模型猜测。当前AI入口不支持清空字段，清空可使用已有业务工具菜单。AI入口每次只提交一张发票的草稿。当前企业、用途内容等参数确认充分后，仍需输入一次 `/confirm`，这是本阶段选择的保存交互，不是赛题要求每次重复确认。

草稿保存前会核对当前发票是否变化；保存事务内也会再次检查草稿快照，避免其他会话的更正被旧草稿覆盖。已确认操作采用唯一操作编号防止重复写入。

## 如何使用

首次在VS Code终端打开项目目录：

```powershell
cd "C:\Users\wsco\Documents\ChatGPT\云账房比赛\tax-harness"
python -m tax_harness init
ollama pull qwen3:8b
python -m tax_harness chat --user U001 --company C001
```

模型准备好后也可双击项目中的 `chat.cmd`。原有 `start.cmd` 仍打开不依赖模型的业务工具菜单。没有增加第三方Python依赖。

推荐演示输入：

```text
查一下发票总额。
查2026年9月发票总额、银行收入和支出。
这个月哪些发票必须补用途？
给F002补一下用途。
用途填：客户资料打印。
还是改成：员工培训资料打印。
/confirm
现在再检查用途缺项。
/exit
```

查看乙企业或只读用户时重新启动：

```powershell
python -m tax_harness chat --user U001 --company C002
python -m tax_harness chat --user U002 --company C001
```

运行自测：

```powershell
python -m unittest discover -s tests -v
python scripts/smoke_test.py
python scripts/verify_ollama.py --model qwen3:8b
```

正常聊天会修改默认业务库；自动验收只修改隔离临时库。如要练习且保留默认数据，可先执行 `python -m tax_harness --db data/practice.sqlite3 init`，然后执行 `python -m tax_harness --db data/practice.sqlite3 chat --user U001 --company C001`。

## 下一阶段目标

下一阶段优先补齐赛题明确要求的持久记忆和知识管理，然后再改善演示入口。

1. 持久任务：为每个用户、企业保存至多一个活动任务，包含月份、目标、待处理和已处理事项、缺失信息。新会话恢复后必须重新查询当前数据；不能从旧任务自动获得修改授权。
2. 明确偏好：仅保存用户明确提出的长期偏好，提供查看、更正和删除，按用户及企业范围隔离，保留来源。
3. 规则维护：提供导入、查找、更新、停用的命令行入口，让规则正文与执行条件保持一致，保留版本，冲突或资料不足时停止判断。
4. 上下文增强：在基础字符预算之上增加任务摘要、来源选择及长对话验证，保证企业、月份和未完成事项不丢失。
5. 可视化演示：在上述能力完成后增加便于评委查看的聊天、当前数据、任务、规则和运行记录入口。

下一阶段验收应至少覆盖：半途退出再继续；切换用户和企业不串记忆；偏好更正与删除在新会话生效；新会话不自动执行旧修改；规则停用后不再引用；新增有效版本后检查结果随之变化；长对话下仍保留正确企业、月份和任务。
